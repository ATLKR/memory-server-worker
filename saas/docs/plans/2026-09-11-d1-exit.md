# D1 execution exit implementation plan

**Goal:** Preserve existing product behavior while replacing active D1 storage with Cloudflare SQLite Durable Objects, retaining the D1 source and a separately isolated Seoul PostgreSQL path.

**Architecture:** The first concrete cutover keeps the existing central relational authority boundary in one explicitly named control object per deployment and moves each existing hot payload shard into a separately named object. R2 remains the durable payload copy. New Agent Memory operation state is already per Space. This is a bounded invite-release compatibility step, not an unlimited database design: every SQLite object still has a 10 GB limit, and the central authority object remains a throughput/capacity constraint. Tenant authority partitioning is a separate required scaling change; never claim this adapter alone solves all scaling or completes Seoul runtime.

**Authorization and scope:** The user has approved active D1 removal and prior rollout/verification. Cloudflare-first storage, exact Space/PAT/SSO authority, independent nested-organization ACL, hard Seoul routing, metering without paid billing, $50/month Cloudflare budget, and preserving old D1 code remain binding. No destructive deletion of existing provider databases, no credential disclosure, no new access to DrCompass. Avoid silent backend fallback and dual writes.

## Design decisions

- User framework steering: real backend HTTP entry uses Hono; new frontend/full-stack work prefers TanStack Start + Router. Consult Cloudflare Agents and Flue for self-managed agent orchestration. Native SQL database coordination remains a plain DO so it does not introduce agent state synchronization or public agent routes into authority storage.
- Preserve the audited SQL and trigger behavior rather than translate authorization ad hoc. Native workerd probe has executed all 25 central migrations and the hot schema successfully. `PRAGMA integrity_check` is unavailable on DO and must not be used as the required gate; supported foreign-key checks, exact schema/data digests, and live product assertions are required instead.
- Use a server-only bounded SQL RPC adapter. `batch` is one synchronous transaction; cursor results are consumed synchronously; prepared values are copied; statements from another adapter cannot enter a batch. Primary reads always reach the named object. No application route accepts SQL.
- Deployment configuration chooses the backend explicitly. In durable mode it builds database adapters without reading any D1 binding; missing/unready objects fail closed. HTTP and scheduled handlers use the same selection. Existing D1 mode remains testable and available for historical code, but final durable configurations contain no D1 bindings.
- Snapshot import must never replay historical rows through live command/audit triggers. An unserved destination is populated under a sealed, bounded import protocol; exact table/column/schema identity, chunk hashes/order, expected row counts and final digest are checked. Foreign keys/derived indexes are verified before it can serve. Import is idempotent by exact chunk identity, never by retrying unknown ordinary writes. After activation imports are closed.
- Cutover freezes writes and scheduled work before a stable snapshot, verifies the target before switching traffic, and preserves the old database as a recovery artifact. A rollback after target writes requires reverse data reconciliation, not blindly restoring an old version. No migration completion claim based only on schema creation.
- Existing hot FTS and tombstone behavior stays functional; R2-only storage cannot silently drop lexical search or late-write fencing. Large raw general transcripts use Agent Memory. Region-locked plaintext never enters these non-Seoul SQL objects.

## Seoul follow-on boundary

The PostgreSQL foundation has no serving handler yet. A usable Seoul route requires a distinct endpoint that never forwards hard-locked plaintext through this Worker, least-privilege private schemas/RLS, TLS and deployment identity attestation, exact caller/Space authority, ingest/search/deletion and model-generation tests. Supabase database placement alone does not attest an ingress or embedding runtime. Do not mark that route ready until its actual deployment is verified.
