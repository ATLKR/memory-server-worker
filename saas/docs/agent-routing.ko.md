# 에이전트 라우팅 · 고객사 공통 동의 · 임베딩 교체

기준: 2026-09-11 사용자 결정. [Cloudflare 저장 구조 검토](cloudflare-storage-research.ko.md)를 보완하는 현재 구현 계약이다. 이전 PostgreSQL 전면 이식 계획보다 이 문서를 우선한다.

## 직원에게 동의를 반복 확인시키지 않는 흐름

고객사 관리자가 이미 확보한 동의의 증빙 참조와 적용 범위를 서비스에 한 번 등록한다. 고객사 공통 플러그인 설정에 `MEMORY_MEDICAL_CONSENT_MODE=organization`을 적용하면 직원은 의료 메모리를 저장·검색할 때 동의 확인 창을 보거나 동의 ID를 입력할 필요가 없다. 플러그인은 의료 분류를 유지한 채 `medicalCloudflareConsent: { "mode": "organization" }`을 자동 적용한다. 이 설정은 기존 동의를 찾는 방식이며 새로운 동의를 생성하거나 고객의 동의 여부를 추정하지 않는다.

서버는 인증된 고객사·직원·Space와 현재 동의 원장을 기준으로 적용 가능한 동의를 찾는다. 고객사 전체 Space 또는 명시된 Space 목록을 대상으로 등록할 수 있으며, 직원은 해당 Space의 기존 권한을 별도로 가져야 한다. 부모 조직의 동의나 권한이 자식 조직에 자동으로 상속되지는 않는다. 개인별 동의 확인이 필요한 고객사가 아니라면 직원별로 같은 동의를 다시 등록하지 않는다.

동의 확인은 백그라운드 요청이다. 등록 버전, 유효기간, 철회 상태와 원문 저장·추출·임베딩·검색에 필요한 범위를 확인한다. 현재 동의가 없거나 범위가 맞지 않으면 본문 전송 전에 중단한다. 이 경우의 고객사 설정 변경은 관리자 업무로 다루며 직원에게 반복 확인을 요구하거나 자동으로 다른 지역에 재전송하지 않는다. 등록된 기간 안에서는 확인 창 없이 계속 이용한다.

개별 동의를 지정해야 하는 연동은 기존 `{ "consentId": "consent-001", "version": 3 }` 형식을 사용할 수 있다. 공통 모드가 명시된 개별 참조를 덮어쓰지는 않는다. 설정을 생략한 기본 의료 경로는 서울이다. `destination: "seoul"`, `requiredRegion: "kr-seoul"`, 서비스가 보유한 서울 고정 규칙은 공통 동의보다 우선한다. `region-locked`와 `uncertain` 분류에도 의료 공통 동의를 확대 적용하지 않는다.

이 동의 기록은 사용자가 정한 제품 정책을 집행하기 위한 자료 구조다. 플러그인이 동의를 법률적으로 평가했다는 표시나 모든 의료정보의 해외 이전을 허용한다는 판단으로 사용하지 않는다.

## 전송 전 프로토콜

1. 사용자 측 에이전트가 전송 전에 의미 단위와 분류를 결정한다. 플러그인은 운영자가 고정한 목적지·Space·경로별 PAT 또는 SSO 토큰을 사용한다. 도구 인수에 URL·토큰·Space를 넣어 목적지를 바꿀 수 없다.
2. 선택한 서버의 `GET /.well-known/memory-routing`을 본문·인증 없이 조회한다. 응답은 `{version:1, protocol:"memory-routing-v1", target:{route,storage,vector,region,ready}}`이며 실제 선택한 저장소 계약과 일치해야 한다. 준비되지 않은 기존 서버에는 토큰과 원문을 보내지 않는다.
3. Cloudflare 의료 경로는 `POST /v1/routing/consent/check`로 `{version:1,requestId,spaceId,consent,operation}`만 보낸다. 원문·검색어·직원의 새 승인 입력은 포함하지 않는다. 서버는 인증 주체에서 고객사를 결정해야 하며, 클라이언트가 고객사 ID를 주장하도록 하지 않는다.
4. 허용 응답은 `{version:1,allowed:true,requestId,spaceId,consentId,consentVersion,operation,expiresAtMs,receipt}`다. 플러그인은 요청/Space/작업/기간을 대조한다. 개별 참조가 지정됐다면 ID와 버전도 일치해야 한다. 공통 모드는 서버가 선택한 정확한 ID·버전으로 실제 MCP 요청을 고정한다.
5. 원문은 그 뒤 선택한 `/mcp`에 한 번만 전송한다. 의료 경로에는 `x-memory-consent-receipt`가 붙는다. 서비스는 receipt의 서명 또는 불투명 서버 저장값, 인증 주체, 요청 ID와 작업, Space, 현재 동의 버전 및 ACL을 **사용 시점에도** 검증해야 한다. 동의 확인 뒤 철회되는 경쟁 상태도 여기서 차단한다. receipt를 동의 원장 대신 무기한 캐시하지 않는다.

요청 ID는 안전한 정수(`Number.MIN_SAFE_INTEGER`부터 `Number.MAX_SAFE_INTEGER`) 또는 UTF-8 128바이트 이하 문자열이다. 동의 확인의 `requestId`와 MCP의 `id`는 값과 타입이 같아야 하며, 응답은 원래 값을 그대로 돌려준다. 숫자 `1`과 문자열 `"1"`은 서로 다른 요청이다. 서버는 원장 내부에서만 ID를 정규화한다. MCP `params._meta`는 직렬화한 JSON 기준 8,192바이트 이하 객체를 허용하며, 권한·본문 해시·제공자 요청에 사용하지 않는다. 검색은 새 receipt마다 새 작업으로 실행하고 receipt 재사용은 차단한다. 저장 재시도는 기존의 명시적 `operationId`를 유지한다.

`consent.ts`의 permit은 위 검사를 위한 **서명되지 않은 내부 검증 결과**다. 그대로 HTTP receipt로 사용하면 안 된다. 실제 receipt 발급·원장 영속화·원자적 재검증은 서버 adapter의 책임이다. 플러그인 요청마다 서버 확인을 하되 사용자 상호작용은 요구하지 않는다. 전송이 시작된 뒤 취소·시간 초과된 ingest는 `routing_write_outcome_unknown`으로 보고하며 자동 재시도하지 않는다.

## 혼합 내용과 동시 검색

서로 독립적으로 이해할 수 있는 내용만 분리 저장한다. 예를 들어 일반적인 업무 선호와 별개의 진료 기록은 다른 메모리로 나눌 수 있다. 한 환자의 진단·약물·부작용처럼 함께 있어야 의미가 유지되는 내용은 강한 제한 경로에 함께 둔다. 원문을 모든 경로에 중복 복사하거나 문장을 기계적으로 자르지 않는다.

여러 조각은 각각 안정적인 `operationId`로 저장한다. 서로 다른 저장소에 걸친 원자적 commit은 보장하지 않으므로 조각별 성공·실패·불확실한 결과를 따로 기록해야 한다. 플러그인 자체가 자동 분류·분할·배치 업로드를 수행하는 것은 아니다. 에이전트가 명시적으로 여러 호출을 구성한다.

복합 질의는 필요한 경로만 병렬 조회한다. 서울 전용 검색어를 Cloudflare에 그대로 broadcast하지 않고, 각 목적지에 보낼 수 있는 별도 질의로 만든다. 결과는 사용자 측에서 출처·지역·세대 표시를 유지해 합친다. 다른 모델의 cosine 점수는 직접 비교하지 않으며, 순위 기반 결합이나 동일한 지역 정책을 만족하는 별도 reranker를 사용한다. 현재 stdio는 최대 4개 동시 도구 호출을 처리한다.

## 임베딩 모델 업그레이드

직접 관리하는 임베딩은 모델명 하나가 아니라 `generation`으로 식별한다. 세대에는 provider, 모델·고정 revision, 차원, 거리 함수, 정규화, chunker version, 범위와 물리 인덱스가 포함된다. 질의와 저장 벡터는 같은 세대의 encoder를 사용해야 한다. 같은 차원의 서로 다른 모델도 호환된다고 취급하지 않는다.

새 모델은 별도 인덱스에 기존 원문으로 재생성한다. 재생성 도중의 수정·삭제를 순서대로 반영하고, 현재 원문의 revision·hash·chunk 수와 실제 인덱스 전체 목록을 대조한다. 불확실한 쓰기·미완료 삭제가 없고 품질 평가가 통과했을 때만 활성 포인터 변경 계획을 만든다. adapter는 그 계획을 실행하는 트랜잭션에서 원문 상태·권한·포인터 버전과 진행 중 작업을 다시 확인해야 한다. 롤백도 현재 삭제를 반영한 인덱스로만 허용한다.

`embedding-generation.ts`는 세대 검증과 전환 계획을 구현한다. 실제 인덱스 생성, 원문 재임베딩, 품질 측정과 atomic pointer 변경은 아직 연결되지 않았다. 관리형 Agent Memory의 내부 모델은 Cloudflare가 관리하므로 공개 API로 임의 모델을 지정할 수 있다고 표시하지 않는다. 별도 Vectorize/pgvector가 필요한 직접 검색 경로에만 자체 세대 교체를 적용한다. [Vectorize 인덱스](https://developers.cloudflare.com/vectorize/best-practices/create-indexes/), [pgvector 의미 검색](https://supabase.com/docs/guides/ai/semantic-search), [Agent Memory API](https://developers.cloudflare.com/agent-memory/api/workers-api/).

## 구현 상태와 운영 연결 순서

순수 라우팅·동의 검증, Agent Memory HTTP transport, SaaS stdio 플러그인, 임베딩 세대 계약에 더해 **조직별 SQLite Durable Object 동의 원장, 관리자 화면, 인증된 동의 API와 의료 MCP 전송 경로**를 구현했다. 실제 Workers·D1·Durable Object·HTTP transport를 함께 실행하는 합성 데이터 테스트를 포함한다. 이것은 공급자 실계정에서의 원문 저장·검색 검증과 구분한다. 현재 운영 서비스의 저장소를 전환한 상태는 아니다. 기존 D1 코드를 보존했으며 활성 D1 제거, 일반 저장소의 Durable Objects 포트와 서울 PostgreSQL runtime은 계속 남아 있다.

관리 화면에서 고객사 공통 적용 범위·유효기간·증빙 참조를 등록하고, 변경 이력과 철회를 원장에 남긴다. 저장 결과가 불확실하면 현재 상태를 다시 읽기 전까지 자동 재시도하지 않는다. 조직이나 계정을 바꾸는 동안 도착한 이전 응답을 새 화면에 표시하지 않는다. 직원별 동의 체크박스는 없다. 원장에는 원문이나 증빙 문서 대신 식별자·해시·버전·작업 결과만 저장한다.

원장의 일회용 receipt는 최대 60초이며 계정·자격증명·조직·Space·작업·요청 ID에 묶인다. 현재 동의와 receipt 소비, 작업 ID 예약은 하나의 DO 트랜잭션으로 처리한다. 기존 D1 권한 조회와 DO 트랜잭션은 서로 다른 저장소이므로 원자적이라고 주장하지 않는다. 전송 직전과 결과 공개 직전에 권한과 동의 버전을 재검증한다. 외부 전송 결과가 불명확한 쓰기는 `unknown`으로 보존하고 다시 전송하지 않는다.

현재 의료 경로는 운영자가 명시적으로 허용한 조직 Space에 한정한 연결 후보이며, 기본 설정은 비활성이다. 일반·서울 경로, 실제 공급자 접근, 삭제·복구와 예산 검증이 끝나기 전에는 `/.well-known/memory-routing`을 준비 완료로 광고하지 않는다. [서버 연결 및 배포 상태](consent-runtime.ko.md)에 설정과 남은 조건을 기록한다.

운영 연결 뒤 실제 계정으로 공통 동의의 무인 적용, 만료·철회 즉시 차단, 서울 고정 우선, 조직/Space 간 오적용 차단, 동의 확인과 사용 사이의 철회 경쟁을 검증한다. 그 전까지 이 플러그인의 readiness 차단을 해제하거나 단순 `ready:true`로 기존 서버를 호환 처리하지 않는다.
