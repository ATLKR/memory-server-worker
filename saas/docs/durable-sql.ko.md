# D1 실행 경로 전환

이번 구현은 기존 SQL 권한·이력·검색 동작을 SQLite Durable Objects로 옮길 수 있게 한다. 백엔드의 실제 HTTP 진입점은 Hono다. 테스트에서는 D1 바인딩 없이 실제 Worker를 실행하고, 서명된 스냅샷 복원 후 SSO·이메일 재인증·PAT·Space 권한·메모리 CRUD·검색·MCP·예약 작업을 검증한다. 로컬 workerd 검증과 실제 배포·데이터 이관의 성공은 별개의 증거다.

## 저장소 선택

`MEMORY_SQL_BACKEND=durable`이면 `MEMORY_SQL` 바인딩과 다음 설정을 모두 요구한다. 설정이 없거나 객체가 봉인되지 않았으면 요청을 거절한다. D1로 자동 복귀하지 않으며 DB/HOT 바인딩에 접근하지 않는다. HTTP와 예약 작업이 같은 선택기를 사용한다.

```json
{
  "MEMORY_SQL_BACKEND": "durable",
  "MEMORY_SQL_DEPLOYMENT_ID": "memory-staging",
  "MEMORY_SQL_EPOCH": "1",
  "MEMORY_SQL_DATABASES_JSON": "{\"DB\":{\"databaseId\":\"control\",\"kind\":\"control\"},\"HOT_01\":{\"databaseId\":\"hot-01\",\"kind\":\"hot\"},\"HOT_02\":{\"databaseId\":\"hot-02\",\"kind\":\"hot\"}}"
}
```

객체 이름은 `sql:<deploymentId>:<databaseId>:<epoch>`다. 운영과 스테이징은 배포 식별자를 공유할 수 없다. Durable 설정에는 D1 바인딩을 둘 수 없고, D1 migration 명령도 실행 전에 거절한다. 기존 D1 소스와 호환 검사는 유지한다.

저장소에 포함된 스테이징 설정 파일은 새 SQL namespace와 이관 공개 키를 추가한 **PREPARE** 구성을 보존한다. 이 파일의 D1 바인딩을 현재 서비스의 배포 상태로 해석하면 안 된다. 2026-09-11의 별도 운영 기록에서는 스테이징을 D1 바인딩 없이 이관·재개하고 실제 PAT/REST/MCP 검증을 완료했다. 해당 검증 소스는 `11354611c403e5558b73a4ac9562a21616893784`다. 이후 배포는 현재 provider 설정과 서명된 운영 기록을 다시 확인해야 하며, 이 파일을 그대로 배포하는 것으로 운영 구성을 재현할 수는 없다. 운영 서비스의 D1 전환과 GA 수락은 별도 단계다.

## 복원과 전환

서버 바인딩 전용 RPC가 SQL을 실행하며 공개 SQL endpoint는 없다. 각 batch는 하나의 동기 트랜잭션이다. 서명된 이관 RPC만 빈 대상 객체에 스냅샷을 넣을 수 있다. 공개 키가 없으면 새 이관을 허용하지 않는다.

스냅샷은 원본 스키마·행·순서·해시·대상 식별자를 고정한다. 임시 테이블에 청크를 넣은 뒤 하나의 트랜잭션에서 테이블 생성, 과거 행 복원, 외래 키 검사, 인덱스·트리거 복원을 수행한다. 과거 명령 행을 현재 트리거로 다시 실행하지 않는다. `rowid`, AUTOINCREMENT 최댓값, FTS 검색 행, 삭제 표식과 미완료 작업을 보존한다. 검증이 모두 끝난 객체만 ready가 된다. 봉인 후 이관으로 기존 DB를 덮어쓰거나 지울 수 없다.

현재 이관 도구의 한도는 행 100,000개, 행 청크 합계 16 MiB, 청크당 500행/512 KiB, 스키마 600개 객체다. 초대 단계에 맞춘 제한이며 큰 데이터의 이관 완료를 주장할 수 없다. 원문 행으로 인덱스를 재구성할 수 없는 external/contentless FTS 및 지원하지 않는 SQL 형태는 사전에 거절한다.

원본에는 점검 진입 게이트를 켠 뒤 control과 모든 hot DB에 정확한 쓰기 차단 트리거를 설치한다. 트리거 정의를 모두 검증하기 전에는 동결로 취급하지 않는다. 임시 차단 트리거는 이름과 SQL 해시가 일치하는 경우에만 복원 대상에서 제외하고, 기존 런타임 보안 트리거는 보존한다. 이관 도중 결과가 불명확하면 기록과 상태를 조회하며 일반 쓰기를 자동 재전송하지 않는다.

R2 백업은 이미 별도 보관한 배포 payload 키에서 HKDF로 분리한 키를 만들어 AES-GCM으로 암호화한다. 배포·DB·세대·실행 ID·계획 해시를 암호화에 결합한다. 임시 이관 서명 키가 없어도 기존 복구 키로 백업을 복호화할 수 있다. 평문 스냅샷·개인 키·자격 증명은 저장소나 운영 로그에 남기지 않는다.

기존 Worker의 외부 쓰기는 SQL 차단 이후에도 끝날 수 있다. 불변 R2 식별자, 영구 purge 표식, 버전별 벡터 ID, 기존 예약·lease·재시도·삭제 확인 상태를 모두 넘겨야 한다. 대기 시간이나 비어 있는 큐만으로 외부 호출 종료를 단정하지 않는다. 대상에서 새 쓰기를 받은 뒤 오래된 D1로 단순 롤백하지 않는다.

## 사용 중인 SQL 객체의 백업과 복구

최초 이관 때의 `durable_sql_state.snapshot_hash`는 이후 변경분을 나타내지 않는다. 현재 데이터를 백업하려면 별도 `MEMORY_SQL_RECOVERY_PUBLIC_KEY`로 검증하는 다음 서버 바인딩 전용 RPC를 사용한다. 공개 SQL·관리 HTTP 경로는 추가하지 않는다.

| RPC | 역할 |
| --- | --- |
| `freezeRecovery` | 한 객체의 현재 SQL 상태를 동결하고 최초 동결 시각을 기록 |
| `recoveryStatus` | 해당 실행의 동결·해제 상태 확인 |
| `prepareRecoveryExport` | 동결된 현재 스키마와 행에서 새 계획·해시 계산 |
| `readRecoveryManifest` | 고정된 계획의 페이지 조회 |
| `readRecoveryChunk` | 계획에 고정된 행 청크 조회 |
| `releaseRecovery` | 백업 확인 또는 운영자 중단 결정에 따른 명시적 해제 |

권한 서명은 `memory-sql-recovery-v1` 도메인, action, 정확한 객체 identity, 실행 ID, 요청 해시와 최대 30분의 유효 구간을 포함한다. 기존 이관 서명을 재사용할 수 없으며 복구 공개 키가 없으면 복구 요청을 거절한다. 개인 서명 키는 Worker에 넣지 않는다. 서명된 source revision은 운영자가 실제 배포 소스와 대조해야 하는 기록이며, 값 자체가 배포 검증을 대신하지 않는다.

동결 확인과 일반 SQL batch 실행은 같은 동기 트랜잭션 안에 있다. 먼저 끝난 batch 전체는 백업에 포함되며, 동결 이후에는 SELECT를 포함한 일반 SQL과 이관 변경 요청을 거절한다. 재시작이나 서명 만료가 동결을 해제하지 않는다. 실행 이력은 객체당 최대 128개를 유지하며, 한도에 도달하면 새 동결 실행을 거절한다. 오래된 해제 요청을 다시 보내도 나중 실행의 동결을 풀 수 없다.

백업 준비는 동결된 실제 카탈로그·행을 읽는다. 행 사본을 원본 객체의 복구 메타데이터에 저장하지 않는다. 계획은 최대 1 MiB이며 UTF-8 바이트를 최대 256 KiB씩 나눠 전달한다. 수신자는 페이지의 바이트를 합친 뒤 디코딩해야 한다. 행 한도는 위 이관 한도와 같고, 각 청크의 실제 해시를 다시 검증한다. 해시 계산 중 동결이 해제되면 결과를 성공으로 반환하지 않는다. 지원하지 않거나 소유 관계를 확인할 수 없는 스키마는 행을 생략하는 대신 거절한다.

복원은 사용 중인 identity를 덮어쓰지 않고 새로운 격리 대상에 수행한다. source와 target 계획의 identity 차이, 행·스키마 해시의 동일성, 암호화 백업의 복호화와 실제 복원 결과를 각각 확인해야 한다. native 테스트는 이관 이후 INSERT/UPDATE/DELETE, 전체 control/HOT 스키마, 이력·FTS·삭제 표식·AUTOINCREMENT, 재시작과 페이지 재조합을 검증한다. 테스트 성공은 실환경 백업·복구 drill의 완료 기록이 아니다.

응답이 유실된 동결 요청은 암호 검증 뒤 늦게 실행될 수 있다. 이때 먼저 받은 `absent` 상태만으로 서비스를 재개하면 안 된다. 운영자는 서명·전송 전에 모든 동결 grant 발급 의도를 보존하고 발급을 닫은 뒤, 그 실행에서 발급 가능한 모든 grant의 최대 만료시각을 지나도록 기다린다. 이후 그 시각 이상의 `notBeforeMs`를 가진 새 상태 요청으로 확인해야 한다. 이미 동결됐다면 별도 서명으로 해제한다. 알 수 없는 결과를 변경 요청의 자동 재전송으로 해결하지 않는다.

## 남아 있는 경계

기존 중앙 권한 DB는 배포당 하나의 control 객체에 남고 hot shard는 각 객체로 나눈다. 객체마다 [10 GB 제한](https://developers.cloudflare.com/durable-objects/platform/limits/)이 있으므로 무제한 확장 구조가 아니다. 향후 tenant 권한 분리가 필요하다. 새 Agent Memory 작업 상태는 이미 Space별 별도 객체를 사용한다.

이 SQL 복구 프로토콜은 consent, Agent Memory Space, 공유 budget 객체나 R2/Vectorize·관리형 Agent Memory를 함께 동결하지 않는다. 전체 서비스의 일관된 복구에는 이 저장소들의 진행 중 작업과 삭제·권한·예약 상태까지 별도 검증이 필요하다. 16 MiB/100,000행을 넘는 현재 상태의 복구도 증명하지 않는다. 출시 운영 한도와 복구 용량의 일치는 별도의 GA 조건이다.

Supabase Seoul의 DB 저장·SQL 실행에는 추가 서울 API 서버가 필요하지 않다. `kr-primary-storage / approved-processors`처럼 저장 위치만 서울로 제한한 경로는 Cloudflare Hono API와 서울 PostgreSQL로 구성할 수 있다. 원문 수신·가공까지 `kr / kr-seoul`로 제한하는 processingBoundary는 별도로 검증해야 한다. PostgreSQL serving의 인증·저장·검색 구현과 실제 임베딩 실행은 아직 출시 검증 대상이며, 이번 비서울 SQL 객체 전환으로 함께 출시된 것은 아니다. 새로운 UI와 자체 agent workflow는 [프레임워크 결정](framework-decisions.ko.md)을 따른다.
