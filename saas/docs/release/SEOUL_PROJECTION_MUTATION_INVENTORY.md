Capture admission requires a trusted composition assertion naming the actual native D1 binding or the repository Durable SQL client/engine, an available atomic batch, and exact database object identity with the service. This assertion is not dynamic proof of arbitrary caller code. The focused tests compose the actual Durable client and `SqlDatabaseEngine.transactionSync` with deterministic local SQLite, including late-failure rollback. No provider execution or production injection has occurred.

Internal projection bounds are 512 combined identity/member/credential keys, 512 raw dependent Space candidates, 128 KiB per source estimate and 512 KiB total source estimate. Account/email/ownership probes use 513-row sentinels. The Space bound precedes target filtering, so a large unselected Space population can conservatively exclude an account. Scalar UTF-8 length arithmetic with a 6x escaping allowance runs before normal JSON construction; only bounded supported policies are parsed. These are representation and availability bounds, not public central quotas. Over-budget or unsupported retained state preserves an accepted central mutation while atomically recording durable exclusion and omitting all normal partial sources/dirty fanout. When a bounded canonical subject anchor and application-valid ASCII account ID of at most 256 characters are available, a small `subject-source-unrepresentable` marker advances that subject to pending. Unsupported account IDs or absent usable anchors retain only the exact durable exclusion; IDs are never truncated or fabricated. Canonical anchor discovery itself is bounded to 513 exact-issuer mappings. Exclusions cannot be cleared by this unit.

Bootstrap subject state includes every exact provider mapping for the account in JS UTF16 order, including opaque newline, BMP and astral subjects. SQL constructs bounded UTF16 sort keys; tests feed the resulting complete arrays into the actual snapshot codec and reject reversed order. Representation estimates account for repeated full identity arrays and subject/address fanout before JSON, capped at 512 potential source rows, 128 KiB each and 512 KiB total. Raw personal/exact-claim organization Space discovery uses a streaming union before the 513-distinct-ID sentinel; claim and membership probes are independently bounded. At most 512 memberships can repeat a bounded 512-Space set, so historical duplicates may require up to 262144 candidate visits. Oversized unselected populations and unsupported Space IDs conservatively exclude accepted changes without partial normal sources or dirtying. Session-only work on an excluded account emits no fresh marker.

Provider discovery bounds the initial historical superset before either event: these cascades cannot create claims, memberships, keys or mappings. Aggregate estimated source rows/bytes count both subattempts and every repeated identity/claim product before JSON. Full-history sentinels deliberately exclude excessive old revoked history rather than scanning past it for live rows. Raw Space discovery retains the same bounded personal/exact-organization union and conservative historical duplicate cost. An excluded account produces no partial normal source or dirty fanout; each actual bounded direct publisher transition remains independently retained. Grouping rows persist only for exact new state advancement, so stale or receipt-only events never consume a source revision. Successful batches clean all transient rows; an unexpected existing operation fails even with no mapped/eligible account.

The future preparer must explicitly recognize the marker and use the existing non-authorizing `entity-head/changed` effect. The future builder/route must reject exclusions and scope pending checks to actual Space dependencies. Existing regional grants can last only their already bounded 60-second lease; these inactive slices make no immediate invalidation or latency claim. Lifecycle negative retention, complete backfill/remediation and every path below outside the coverage table remain required before activation.

The reviewed v2/v3 plans remain binding with the parent task's `seoul-sso-projection-v3-pending-head-amendment.md`: hash the effective source record after its database revision is assigned, then hash the separate transport envelope. ## Trigger closure and non-HTTP writers

The effective trigger chain matters as much as the entry method. `cascade_email_revocation` revokes exact email-bound memberships and credentials. `cascade_membership_revocation` then revokes exact membership-bound credentials and domain-manager rows. `release_scim_membership_revoked` and `release_share_membership_revoked` in `release-schema.sql:224,291` revoke SCIM keys and creator-membership shares. Lifecycle triggers can update all of these in one accepted command. Capture each changed source row once under the source command identity; do not hash a parent command as a substitute for the changed bindings.

The base schema also permits trusted SQL updates to `accounts.disabled_at`, `organizations.disabled_at`, membership role/expiry/revocation and credential permission/expiry/revocation/reauthentication. They have no additional production public writer found in this bounded source inventory. Future administrative, repair, import or backfill writers must be instrumented too. Database-time expiry can remove authority without a write: snapshot construction and every regional action must enforce expiry directly, with bounded refresh/dirty scheduling; no fabricated write revision is required solely because time passed. Existing immutable identity/Space ownership guards must remain.

Migration 0026's only source trigger is on the **new** `release_seoul_authority_changes` table: each inserted change creates or advances its head to a null pending digest. The focused tests exercise it with `recursive_triggers=ON` and `OFF`. That does not prove central cascade hooks exist or verify live D1 recursion settings. The next unit must use explicit post-write `INSERT ... SELECT` capture or separately verified trigger mechanisms, with real accepted/denied/cascade rollback tests for every applicable row above.

Production source writers omit `revision`; SQLite assigns it. The monotonic check runs in `AFTER INSERT` against that assigned value, not an undefined preassignment `NEW.rowid` sentinel. The test also rejects a lower unused explicit revision and verifies the failed insertion changes neither source nor head. An exact source-command/event replay compares supplied immutable fields and is ignored; dependent authoritative/capture writes must still be replay-gated because `RAISE(IGNORE)` is not rollback. See SQLite's [trigger cautions](https://www.sqlite.org/lang_createtrigger.html).

## Persistence contract and remaining atomic integration

1. **Accepted mutation batch, partially integrated:** the optional paths above execute the unchanged authoritative statements together with bounded before/after capture; insert closed effective source records with DB-assigned revision and fresh batch/subattempt identity; 0026 advances the exact head to `payload_sha256=NULL`; dirty bounded supported Spaces using the newest actual inserted revision. Acceptance uses an exact newly inserted receipt/key identity and, for V2, exact lifecycle state advancement, never `changes()` or an unassigned rowid. Capture statements cannot replace the original service result. All staging rows are explicitly removed before commit, and any late SQL failure rolls back the original command, sources, heads and dirty state. Other central methods remain uncaptured. Dirty capture is not attached automatically to a source change because affected Spaces depend on the effective account/organization/binding and old dependencies.
2. **Prepared source batch, not yet implemented:** validate immutable source core including revision in JavaScript, compute the source SHA, form a separate head transport envelope and transport SHA. Insert `release_seoul_prepared_sources` and `release_seoul_projection_events` atomically. Their deferred, bidirectional foreign keys require event identity, assigned source revision, source digest and transport digest to match at commit; the non-null source digest identifies a head event under the event-shape constraint. Source event IDs cannot name snapshot envelopes in either insertion order: an existing snapshot also prevents later source insertion. Both legitimate event-first and binding-first preparation work. Update a head only where its revision/event still match and its digest is pending. Historical negatives may be prepared after a newer head without changing that head. A head can finalize only to the matching prepared source digest; prepared bindings and event bytes cannot be updated, deleted or replaced with changed data.
3. **Zero-row comparison:** a failed conditional insert does not roll back D1 `batch`. Every dependent head, delivery, sequence or dirty-capture write must use the exact successfully inserted candidate tuple or a proven trigger. The local schema test demonstrates conditional dependent writes make zero changes; it is not a complete production preparer or publish query.
4. **Snapshot store, not yet implemented:** one first-primary session reads global and dependency heads, current target and per-Space sequence around stable base-table reads. A positive envelope/publication refuses any pending head (this foundation conservatively blocks on any global pending head). Claim with database time, lowercase 128-bit fence and at most 15 seconds. Compare global/dependency/target/fence/current-sequence state again and atomically insert immutable event plus delivery, advance sequence by one and capture only the examined dirty revision. The schema enforces source binding, exact transport replay, uniqueness, monotonic sequence, 60-second duration and bounds; it does not yet enforce that full multi-row publish predicate or receipt freshness.
5. **Delivery runtime, not yet implemented:** state defaults to pending, known pending and uncertain stay explicit, terminal receipt bytes are immutable, and attempts/fences are bounded. The 100-attempt field ceiling is a storage limit, not an enabled retry policy. SQL enforces a 15-second fence bound and monotonic counts. An expired Space or delivery claim requires a fresh token and database-time `claimed_at`; Space takeover additionally names the current dirty revision. Space replacement insertion cannot reuse the expired token. Active same-token renewal retains the original timestamp and therefore cannot extend beyond its original 15-second window. A fresh delivery claim advances attempts by exactly one; active renewal leaves attempts unchanged. The dispatcher must still apply token ownership predicates, attempt/backoff policy, lease validity, head-first delivery and GET-first unknown-commit reconciliation. Receipts and payload shapes/hashes require the future codec; SQLite only enforces identity linkage, format/size and byte immutability.
6. **Backfill and rollout, not implemented:** existing data gets no fabricated source history, target selection, event, receipt, grant or lease. Resolve retained identity/digest conflicts explicitly.
