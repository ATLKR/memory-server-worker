# Inactive D1 snapshot store

`createSeoulProjectionSnapshotStore(database, adapter)` creates one trusted same-database primitive that composes a canonical v3 snapshot for a dirty managed Space and publishes it through the projection events/deliveries sequence plus the per-Space publication watermark. It has no dispatcher, delivery runtime, public route, regional authority or background execution. The adapter is the fixed `native-d1` / `durable-sql` caller assertion used by the other inactive projection modules; it is not a cryptographic provenance or authorization proof. Construction validates that the supplied database exposes `prepare`, `batch` and `withSession` and refuses anything else with `seoul_snapshot_store_adapter_unsupported`.

Apply the complete forward migration chain through `0036_seoul-projection-publication-schema.sql` before using this unit. The migration adds only the transient `release_seoul_snapshot_stage` table and advances `release_meta.version` to 36; publication uses the preexisting events/deliveries schema and the new `release_seoul_published_snapshots` watermark with its triggers. Projection state remains `backfill-required`.

## Publish command and validation

`publish(unknown)` owns exactly `spaceId` before any asynchronous work; a malformed, non-object or extra-field input makes zero database calls. A schema version below 36 reports `schema_missing` without further reads.

Publication proceeds through first-primary sessions: observe stage/space/dirty/pending/fence/watermark, claim the projection fence, reobserve under the claimed fence, build the snapshot on a stable base-table read, then apply one atomic publication batch. A post-write observation classifies the durable outcome. The stage table wraps the publication batch; retained staging on entry returns `staging_retained` and the batch's no-residue assertion returns it again after a rolled-back attempt. There is no automatic stage cleanup.

The fence claim is `release_seoul_projection_lock`: a lowercase hex fence, database-time `claimed_at` equal to the snapshot `issued_at`, a 15-second lease inside the schema bound, and `claimed_revision` naming the current dirty revision. Each claim statement pins one database-time scalar so `claimed_at`/`expires_at` cannot drift apart mid-statement. An occupied live fence returns `fence_held`; an expired fence is replaced in place.

## Snapshot composition

The builder reads only through `withSession('first-primary')` and inside bounded statements. These are advisory reads — each statement is its own first-primary query, and a concurrent central write may move base state between them. That is safe because the publish batch re-verifies every state the reads inform before any durable row lands: the fence tuple, the examined dirty revision, the target tuple, the sequence, event absence, the global pending-head rule, every pinned dependency head, and — for the states that carry no authority head — the exclusion roster and the `disabled_at` consistency of every account and organization named in the payload. A dependency graph above the bounded head population reports `unrepresentable` rather than a missing-dependency verdict. Disabled or unscoped-out credentials are skipped, never partially granted. Personal Spaces join `accounts` so a disabled owner suppresses its own credentials; the owner account is always present in the dependency graph so a deselected or fully revoked Space still publishes a valid zero-grant snapshot. Organization credentials require live exact membership, verified email, enabled account and organization, and `owner`/`admin` role for ingestion grants; grant expiry is the minimum of credential and membership expiry. Any excluded account among the dependency set refuses the whole publication with `account_excluded`; this store never publishes a partial positive authorization graph.

Every needed authority head must exist and carry a prepared payload digest at claim time; missing dependency rows report `dependency_missing` and pending digests report `heads_pending`. The publish batch additionally refuses any pending head globally, matching this foundation's conservative pending rule. The canonical v3 envelope carries `issuer=https://auth-api.allen.company`, the declared Seoul residency/policy block, exact grant tuples and `expiresAt=issuedAt+60000`. The schema separately enforces the 60-second event duration, snapshot shape, sequence monotonicity and byte bounds.

## Atomic publication and classification

The publication batch inserts the stage row, the immutable snapshot event and its delivery row, initializes or advances the watermark to the claimed sequence, captures only the examined dirty revision, and removes its own stage. A guarded completion UPDATE writes `complete_guard` — the column's `CHECK(complete_guard=1)` makes an incomplete publication abort the whole batch — and a consumed SELECT asserts the stage row still exists before its own DELETE. Residue is then detected by a fresh post-batch observation rather than an in-batch row. Sequence advance uses insert-on-absent plus update-from-`seq-1`, so a repeat publish after fence expiry produces the next immutable event rather than a watermark error.

Results are `published` (with the exact event/sequence/revision fields), or one of `staging_retained`, `space_missing`, `not_dirty`, `heads_pending`, `dependency_missing`, `account_excluded`, `fence_held`, `unrepresentable`, `stale`, `sequence_conflict`, `event_conflict`, `request_limit`, or `uncertain`. `stale` marks a source/target/sequence shift that must be retried; `sequence_conflict` means another publication already owns or advanced past the claimed sequence; `event_conflict` means a different event holds this event identity. A competing sequence row or event without the matching watermark is `stale` or `sequence_conflict`, never `published`.

After any thrown batch or malformed response the store performs sequential first-primary readbacks — never parallel sessions, which could nest transactions in the Durable adapter or observe different commit points. A committed claim fence is honored and publication continues; a lost publish acknowledgement still returns `published` when the exact event, delivery, watermark and dirty capture all prove the write. Before reporting `uncertain` the store re-checks the exclusion roster against the payload's account list so an exclusion race produces the terminal `account_excluded` verdict. No mutation is retried blindly, no identifier is regenerated, and an indeterminate outcome stays `uncertain` rather than claiming success or inventing rollback. A later dirty advance after a committed publish is a new change, not evidence that the earlier publish failed.

## Limits and remaining work

All reads and writes stay inside the shared request limits (100 statements, 100 values per statement, 100,000 SQL bytes per statement, 1 MiB request). Dependency enumeration binds credential, account, email, membership, identity and head keys before semantic checks; there is no whole-table scan, guessed rowid or `changes()` authority.

Focused tests exercise real Durable SQL execution, recursion ON/OFF, retained staging, fence contention and expiry, pending heads, excluded accounts, personal and organization canonical payloads, zero-grant deselection, dirty and pending-head races between claim and publish, competing sequence/event injection, exclusion and disablement races between build and publish, injected stage residue, and lost claim/publish acknowledgements. These tests do not constitute delivery, admission or live deployment.

This store completes the D1 publication boundary only. Still outstanding: the delivery/dispatcher runtime and its receipts, the coherent final C installation's ordinary admission/public-authorizer predicates (the caller-facing snapshot dispatch entry now exists as the inactive `postgres/projection-v3/snapshot-dispatch.sql` draft), public route and authorization gates, backfill and rollback/operational recovery, residency and cost evidence, and separate live acceptance. Nothing here activates a Seoul path.
